## 2. 引擎目前對「實體」的依賴（現況）

引擎只使用：`spawnPet`、`bringStray`、`despawnPet`、`entityExists`、`playAnimation(ref, animId)`。它把實體當成**不透明的參考**，不讀位置也不讀狀態。所以**目前契約不需要改**，M1 可以在現有契約下完成。

| 候選函式 | 引擎用來做什麼 | 啟用條件（需要的證據） |

## 3b. 遊戲 → 引擎的事件（審查 major，已部分處理）

現有契約只有「引擎 → adapter」的單向呼叫。本機 session 審查指出：缺少「遊戲 → 引擎」的通知。

| 事件 | 狀態 | 說明 |
|---|---|---|
| `slot_changed`（玩家換了存檔） | ✅ **已實作**（選用 `slotId()` ＋選用 `subscribe`） | 這是引擎**現有缺陷**：`App` 只在啟動時讀一次存檔，換存檔後會讀寫錯誤的欄位。修法：每次對外呼叫先比對 `slotId()`，不同就重載該存檔的狀態，**且絕不把舊狀態寫進新欄位**；若新存檔無法讀取（例如較新版本寫的）就暫停、不碰它。`subscribe("slot_changed", fn)` 只是讓反應更快，不是必要。6 項測試（`tests/test_slots.lua`） |
| `world_loaded`（進入世界） | ⏸ 暫緩 | 等 M1-3a 知道怎麼偵測再說；目前不需要 |
| `zoi_interacted`（Zoi 與貓互動） | ⏸ 暫緩 | 取決於 M1-3b 與 P9（能否加互動選項） |

**兩種情況要分清楚**（本機 session 審查 a240f2f 的 major）：
- adapter **沒有存檔概念** → 根本不要定義 `slotId`（引擎用 `Api.hasSlots()` 判斷），行為與以前完全相同。
- adapter 有存檔概念，但**目前沒載入存檔**（讀取畫面、主選單）→ `slotId()` 回傳 `nil`。引擎進入**暫停**：不 tick、不讀、不寫、不扣款，對外呼叫回傳 `no_save`，介面顯示「載入存檔後才會看到你的寵物」；等到 `slotId()` 回傳非 nil 才恢復。`slotId()` 若丟出錯誤，視為「沒載入存檔」（保守）。
換存檔時也不再沿用上一個存檔的亂數狀態（nit ②）。nit ①（呼叫中途存檔被換掉）寫成註解：遊戲的 Lua 是單執行緒、對外呼叫不會讓出執行權，所以呼叫開頭同步與結尾存檔之間 slot 不會改變。

**adapter 方（本機）要做的事**：實作選用的 `slotId()`（有存檔回字串，沒存檔回 nil）；可選擇實作 `subscribe(event, fn)`。依擁有權規則，這是「新增選用函式」，本機作者＋通知即可。

## 4. 結論與下一步
- **「實體貓」資訊現在不改契約。** 等 M1-3b 有結果，再依證據把候選函式升為正式提案（新增選用函式＝本機作者＋通知；改必要函式＝雙方 review）。
- 若 M1-3b 結果是「貓不會自己走動、沒有 AI」，則 `setBehaviorHint` 退化為「播放動畫」（現有的 `playAnimation`），不必新增函式。
