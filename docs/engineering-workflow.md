# 開發分工與規則（v2.0）

> 狀態：**v2.0 採用**（2026-10-20，PO 決定，見 ADR 0006）。雲端 session 已退出，只剩 PO 與一個本機 session；
> 路線改為官方 ModKit（ADR 0005）。v1.x 的雲端分工、四眼原則、session 間通知已廢止（見文末變更紀錄）。
> 精簡版在 `CLAUDE.md`。

## 1. 角色

| 角色 | 由誰擔任 | 負責 |
|---|---|---|
| **產品負責人（PO）** | 使用者 Tim | 範圍、玩法規格、優先順序、**一切對外與不可逆的決定**、每次合併 |
| **開發者（Dev）** | 本機 session（跑在使用者電腦） | 寫程式＋測試、透過 MCP 在遊戲與 ModKit 裡實測、文件、ADR、CHANGELOG、**自我審查** |

## 2. 分支與合併（trunk-based、短命分支）

- 預設分支 `ccr-d0885a2d-yzygl2` 永遠可用（測試全綠），**Dev 絕不直接推送**。
- 分支命名：`feat/`、`fix/`、`docs/`、`chore/`；一個分支只做一件事，存活不超過數天。
- **Dev 可以直接推送功能分支**，不必每次詢問。
- 合併：**squash merge**，Conventional Commits（英文）。合併前必須：§3 完成標準全部成立＋**PO 說「可以合併」**（每次都問）。
- 不改寫已推送分支的歷史；需要時新增 commit，不 force push（除非 PO 明確同意）。
- 未經 PO 要求不開 PR／Issue。

## 3. 完成標準（合併前必須全部成立）

1. 測試全綠（本機 `py -I tests\run.py` 或 `lua ... tests/run.lua`，**看最後一行**）；推送後 CI（`.github/workflows/test.yml`，含 Windows）也要綠。
2. 新增邏輯有測試（用 `adapters/mock.lua`）；測試要真的測到行為——寫完確認「改回舊行為時它會失敗」。
3. en／zh-TW 字串齊全、佔位符一致（測試會擋）。
4. 動到存檔結構 → 有 migration＋測試。
5. 動到遊戲介接（`adapters/inzoi.lua`）→ 每個函式標明「已驗證（遊戲版本、日期、依據）／未驗證」；`caps` 只有遊戲內實測後才可為 true。
6. 文件同步（README／docs／CHANGELOG 的 `Unreleased`）。
7. Dev 自我審查：對照 `CLAUDE.md` 規矩、驗證狀態有依據、沒有把推論寫成事實。

## 4. 測試策略

| 層 | 內容 | 在哪跑 | 頻率 |
|---|---|---|---|
| 單元／行為 | 引擎（需求、個性、老化、收容所…）＋模擬 30 天 | CI＋本機 | 每次 push |
| Adapter 契約 | 用假的官方 Lua API 驗證 `adapters/inzoi.lua`；**假資料必須來自 MCP 或官方文件的實際輸出，並註明來源與遊戲版本** | CI＋本機 | 每次 push |
| 遊戲內探勘／驗收 | 透過 `inzoi-game`、`inzoi-modkit` MCP 執行 `docs/phase0-probe.md` 與之後的驗收清單；結果寫 `docs/phase0-results.md` 或 `docs/qa/results/` | 只有本機 | 第 0 階段、每個 release 前、每次遊戲大更新 |

## 5. 什麼事要問 PO

- 玩法與規格（隻數、老死、數值、經濟、新功能）。
- 啟動遊戲、進存檔（見 §6）。
- 下載或安裝任何東西（說明檔名、來源、大小）；修改使用者的全域設定。
- **發佈**到 CurseForge／Nexus／任何外部平台。
- 合併進預設分支；改寫 git 歷史、刪除分支、改預設分支名稱、開啟 branch protection。
- 永遠不做：取得或使用 AES 金鑰、散佈 KRAFTON 資源。

## 6. 遊戲操作的同意層級

| 層級 | 內容 | 同意 |
|---|---|---|
| T0 | 讀檔、讀 log、跑離線測試、改程式、讀官方文件 | 不需要 |
| T1 | 啟動遊戲停在主選單、開 ModKit 編輯器；透過 MCP **只讀**查詢 | 每個工作階段問 PO 一次 |
| T2 | 進存檔；透過 MCP 執行會改變遊戲狀態的指令（生成、移動、互動、改數值）；不在連線遊玩時進行 | **PO 在電腦前同意**，並**先備份兩個存檔資料夾**、核對檔案數與大小 |
| T3 | 安裝／移除／更新工具（ModKit、UE4SS…），或動遊戲資料夾 | **PO 明確同意**，做法要可還原 |

載入存檔時**絕不強制結束遊戲**。

## 7. 溝通與紀錄

- **時間一律用台灣時間（UTC+8）**（git、CI、log 的原始時間戳保持原樣，引用時換算）。
- 需要 PO 的事直接在對話裡問，一次一題，附上建議與理由。
- 每個重要決定寫成 **ADR**（`docs/adr/NNNN-標題.md`：背景、決定、後果、決定者與日期）。

## 8. 版本與發佈

- SemVer，`0.x` 期間不保證相容；`CHANGELOG.md` 採 Keep a Changelog。
- 相容性表：模組版本 ↔ inZOI 版本（`docs/compatibility.md`）。
- Release＝tag＋打包檔＋CHANGELOG＋相容性表；**發佈由 PO 決定**。

## 9. 工程要求

1. **停用方式**：遊戲內模組管理器可以停用 mod（官方機制）；`caps` 預設全 false。
2. **啟動 log**：mod 版本＋遊戲版本＋caps，方便回報問題。
3. **未驗證的遊戲版本只做虛擬寵物**（caps 全 false），直到該版本有遊戲內證據並登錄在 `docs/compatibility.md`。
4. **存檔有版本號與 migration**；讀失敗＝視為沒有寵物，絕不讓遊戲崩潰。
5. **回復計畫**：每個 release 的說明都要寫怎麼完全移除。

## 10. 風險登錄

| 風險 | 緩解 |
|---|---|
| 官方 Lua 碰不到動物或生成 | 方案 C（虛擬寵物）為底線；第 0 階段先確認 |
| 遊戲更新改動 Lua API | adapter 集中、契約穩定；每次大更新跑驗收清單 |
| 存檔損毀 | T2 前備份；存檔讀失敗不崩潰 |
| 官方文件與實測不一致 | 以實測為準，文件記下差異與日期 |

## 11. 目前里程碑：第 0 階段（官方 ModKit）

照 `docs/phase0-probe.md`：P1（工具與指令）→ P7（計時、存資料）→ P8（UI 按鈕）先確認底線，再 P2–P6、P9（真寵物的可能性），P10 之後再說。完成條件：`docs/phase0-results.md` 填完、決定方案 A／B／C 並寫成 ADR。
